1. SEGURANÇA — ANÁLISE PROFUNDA
🔴 CRÍTICO #1 — XSS em footer.php (interpolação direta em echo)
Arquivo: footer.php — linhas 44–53
php// CÓDIGO PROBLEMÁTICO (atual)
foreach ($redes_sociais as $rede => $dados) {
    $info = get_rede_social($rede);
    if (!empty($info['link'])) {
        echo "<li class='ms-3'><a href='{$info['link']}' class='link-light btn'

Problema: $info['link'], $info['nome'] e $info['icone'] são interpolados diretamente no HTML sem escaping. Se qualquer um desses valores vier de input do admin/usuário (opções do Customizer, meta do banco), um atacante pode injetar javascript:alert(1) em href ou "><script> nos atributos.
Impacto real: XSS Stored, executado em todos os visitantes do site. Risco de roubo de sessão, defacement, injeção de malware.
php// CÓDIGO CORRIGIDO

    if ( ! empty( $info['link'] ) ) {
        printf(
            '<li class="ms-3"><a href="%s" class="link-light btn" target="_blank" rel="noopener noreferrer" aria-label="%s"><i class="%s" aria-hidden="true"></i></a></li>',
            esc_url( $info['link'] ),
            esc_attr( $info['nome'] ),
            esc_attr( $info['icone'] )

    }
}

🔴 CRÍTICO #4 — CSRF: Verificação de cookie LGPD sem httpOnly + lógica server-side frágil
Arquivo: footer.php — linhas 62–73
php// CÓDIGO PROBLEMÁTICO (atual)
<?php if (!isset($_COOKIE['lgpd_consent'])) : ?>
<div id="lgpd-consent-banner" class="d-none">
    ...
    <button id="lgpd-accept">Aceitar</button>
    <button id="lgpd-reject">Rejeitar</button>
</div>
<?php endif; ?>
Problemas em cascata:

O cookie lgpd_consent é definido via JavaScript no lado do cliente sem a flag httpOnly e Secure, tornando-o acessível por XSS.
A verificação isset($_COOKIE['lgpd_consent']) no PHP é trivialmente bypassável: qualquer cookie com esse nome suprime o banner, inclusive cookies corrompidos ou injetados.
A LGPD exige registro de consentimento com timestamp e escopo, não apenas um cookie booleano.
O banner abre com class="d-none" — se o JS falhar, nenhuma opção de consentimento é apresentada, violando o princípio de privacy by design.

php// SOLUÇÃO CORRIGIDA
// No functions.php — registrar endpoint REST para salvar consentimento
add_action( 'rest_api_init', function() {
    register_rest_route( 'tecnoinfor/v1', '/lgpd-consent', [
        'methods'             => 'POST',
        'callback'            => 'tecnoinfor_save_lgpd_consent',
        'permission_callback' => '__return_true',
    ] );
} );

function tecnoinfor_save_lgpd_consent( WP_REST_Request $request ) {
    $choice = sanitize_text_field( $request->get_param( 'choice' ) );
    if ( ! in_array( $choice, [ 'accepted', 'rejected' ], true ) ) {
        return new WP_Error( 'invalid', 'Invalid choice', [ 'status' => 400 ] );
    }
    // Definir cookie httpOnly via PHP (seguro contra XSS)
    setcookie(
        'lgpd_consent',
        $choice,
        [
            'expires'  => time() + YEAR_IN_SECONDS,
            'path'     => '/',
            'secure'   => is_ssl(),
            'httponly' => true,
            'samesite' => 'Lax',
        ]
    );
    return [ 'status' => 'ok', 'choice' => $choice ];
}

🔴 CRÍTICO #5 — _e() / __() sem escaping em output direto
Arquivo: page-contact.php, single-software.php, footer.php
php// PADRÃO PROBLEMÁTICO — encontrado em pelo menos 15 ocorrências
<?php _e('Contact Information and Form', 'tecnoinfor'); ?>
<?php echo __('Tecnoinfor', 'tecnoinfor'); ?>
<?php _e('Send Us a Message', 'tecnoinfor'); ?>
Problema: _e() e __() não fazem escaping. Se as strings de tradução em .po/.mo forem comprometidas (por um plugin de tradução malicioso ou acesso ao arquivo), código arbitrário pode ser injetado no output. O correto é usar esc_html_e() e esc_html__().

<?php esc_html_e( 'Contact Information and Form', 'tecnoinfor' ); ?>
<?php echo esc_html__( 'Tecnoinfor', 'tecnoinfor' ); ?>
// Para atributos HTML:
<?php esc_attr_e( 'Toggle navigation', 'tecnoinfor' ); ?>

Arquivo: single-software.php

    'post_type'  => 'planos',
    'posts_per_page' => -1, // ← sem limite!
    'meta_query' => [[ 'key' => '_plano_software_id', 'value' => get_the_ID() ]]

Impacto: Uma única visualização de página de software gera no mínimo 5 queries ao banco + a query principal do post, além de múltiplas chamadas a get_post_meta() dentro de loops (padrão N+1). Em um site com 50 planos e 20 funcionalidades cada, isso pode gerar 100+ chamadas ao banco por page load.
Solução — consolidar com transients e pre-loading:
php// SOLUÇÃO: Centralizar dados em um único transient por post
function tecnoinfor_get_software_page_data( int $software_id ): array {
    $cache_key = "software_page_data_{$software_id}";
    $data      = get_transient( $cache_key );

    if ( false !== $data ) {
        return $data;
    }

    // Uma única query para changelogs
    $changelog = get_posts([
        'post_type'   => 'changelogs',
        'numberposts' => 1,
        'meta_key'    => '_related_software',
        'meta_value'  => $software_id,
        'orderby'     => 'date',
        'order'       => 'DESC',
    ]);

    // Uma query para planos com todos os meta em um go
    $planos = get_posts([
        'post_type'   => 'planos',
        'numberposts' => 20, // limite explícito
        'orderby'     => 'menu_order',
        'meta_key'    => '_plano_software_id',
        'meta_value'  => $software_id,
    ]);

    // Pre-load meta em batch (evita N+1)
    if ( $planos ) {
        $plano_ids = wp_list_pluck( $planos, 'ID' );
        update_postmeta_cache( $plano_ids ); // carrega todos os meta de uma vez
    }

    $data = compact( 'changelog', 'planos' );
    set_transient( $cache_key, $data, HOUR_IN_SECONDS );

    return $data;
}

// Invalidar cache ao salvar/atualizar post
add_action( 'save_post_planos',     fn( $id ) => delete_transient( "software_page_data_*" ) );
add_action( 'save_post_changelogs', fn( $id ) => delete_transient( "software_page_data_*" ) );

5. BANCO DE DADOS — META QUERIES E INDEXAÇÃO
🟠 ALTO — Meta queries sem índice em campos relacionais
php// Padrão encontrado em múltiplos templates:
'meta_query' => [[
    'key'     => '_related_software',
    'value'   => get_the_ID(),
    'compare' => '=',
]]
A tabela wp_postmeta não tem índice em meta_value por padrão. Queries que filtram por meta_value fazem full table scan. Para o campo _related_software que é um relacionamento entre CPTs, a solução correta é usar taxonomias:
php// SOLUÇÃO ARQUITETURAL — usar taxonomia ao invés de post_meta para relacionamentos
// Em vez de _related_software como meta, registrar uma taxonomia 'software_ref'
register_taxonomy( 'software_ref', [ 'changelogs', 'faqs', 'downloads' ], [
    'public'       => false,
    'hierarchical' => false,
    'rewrite'      => false,
] );

// Query com taxonomia usa índice nativo:
$faq_query = new WP_Query([
    'post_type' => 'faqs',
    'tax_query' => [[
        'taxonomy' => 'software_ref',
        'field'    => 'slug',
        'terms'    => get_post_field( 'post_name', get_the_ID() ),
    ]],
]);

10. RESUMO EXECUTIVO FINAL
Contexto: O tema tecnoinfor é um tema WordPress clássico customizado para o segmento de software de gestão (funerárias, óticas, igrejas). Conta com 8+ Custom Post Types, integração com Customizer, Bootstrap 5, e um sistema de planos de assinatura.
Principais achados:
O projeto demonstra intenção arquitetural correta — modularização em inc/, separação de CPTs em arquivos individuais, uso de template-parts — mas a execução apresenta falhas graves especialmente em segurança e performance.
O problema mais crítico é o padrão de output sem escaping, presente em pelo menos 20 pontos do código, que configura vulnerabilidade XSS real. O segundo problema mais urgente é o padrão N+1 no single-software.php, que pode degradar severamente o TTFB em produção com volume de dados real.
A ausência total de testes e CI/CD é um risco operacional grave: qualquer deploy pode introduzir regressões sem detecção automatizada.
